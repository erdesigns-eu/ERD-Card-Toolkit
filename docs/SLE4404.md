# SLE4404 contact-memory profile

`TSle4404CardReaderWriter` implements the distinct **ACR38x CCID selector 08**
protocol. It is not an ordinary SLE4442 profile and does not claim ACR39 support.
Supply a connected `ICardTransport` implementing `ICardTransaction`, an actual
`ReadableBytes` window (1–256), and operation-specific `TSle4404AccessLayout`
fields from the chip/application documentation. There is no guessed layout,
default code or automatic capacity detection.

| Operation | Behavior |
| --- | --- |
| ReadMemory | Public read with empty user code, or one supplied two-byte code in the same transaction |
| VerifyUserCode | Read four-bit error-counter budget, present code once, require post-command counter byte FF |
| ProgramMemory | Exact expected-before comparison, one-to-zero programming only, chunks up to 128 bytes, independent read-back |
| EraseScratchPad | Explicit known scratchpad address/length, compare expected-before, one FF-D2 erase and complete-area FF check |
| EraseApplication | Explicit user/memory error counters and application area; present two-byte user code then four-byte memory code once, verify formerly non-FF application area became FF |

Every operation resets/selects once in an exclusive transaction. Authentication is
not retained between calls. Supplied codes, expected-before and replacement arrays
are copied before I/O; local credential/command copies are cleared afterwards.
Backend copies are outside this guarantee. No automatic retry occurs.

## Codes, budgets and erase evidence

User-code commands use fixed ACS key address 08; memory-code commands use 28.
Layout configures readable **counter/area** locations, not these fixed key addresses.
User error-counter masks must contain four bits. The memory error counter is eight
bytes (64 bits) and **cannot be restored**. `MinimumUserCodeAttempts` (1–4) and
`MinimumMemoryCodeAttempts` (1–64) control pre-attempt budgets; their defaults are one.
Successful user verification requires FF counter read-back, not only status 9000.
Presenting codes is itself a state-changing operation and can consume retry bits.

Application erase checks the memory budget before attempting either code. It refuses
an expected or actual already-erased area because all-FF contents could not prove
that the supplied memory code caused an erase. The configured erase area may not
include fixed code storage or configured counters. Erase verification covers only
the explicitly declared readable area; correctness of that layout is the caller's
responsibility. Scratchpad address 02 is described as typical by ACS, not installed
as an API default. A verified already-erased scratchpad is a no-op.

Any failure after programming/erase dispatch, including transaction release, raises
`EMemoryCardWriteUncertain`; completed read-back evidence is retained in the error.
Dispatched user authentication failures remain explicit authentication errors.
Do not retry an uncertain operation automatically. Zero-to-one programming requires
an appropriate explicitly requested erase, never an implicit erase fallback.

## Examples and validation

`examples/memory/InspectSle4404.dpr` supports offline `--window` inspection and an
explicit `--reader ... --dialect acr38-ccid --window ...` public read. The VCL memory
page also supports SLE4404 public snapshot/range reads. Codes and irreversible erase
operations are available through the API, not automatically invoked by these demos.
Physical chip/reader tests and native Delphi execution remain pending.

`tests/memory/Sle4404.Tests.dpr` executes independent literal command transcripts,
code-budget checks, protected/public reads, programming/erase read-backs, all I/O
failure boundaries, every read-back bit, chunking, caller ownership and release
uncertainty. These tests supplement Delphi and hardware validation.

Reference: [ACS ACR38x CCID API 6.05](https://www.acs.com.hk/download-manual/3450/REF-ACR38x-CCID-6.05.pdf),
section 9.3.8. No new firmware compatibility is inferred from a shared reader name.
