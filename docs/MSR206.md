# MSR206/MSR605 serial reading and programming

`TMsr206MagStripeAdapter` implements concrete standard ISO framing over
`IMagStripeSerialPort`. `CreateWindowsMagStripeSerialPort` supplies native Windows
COM I/O without a vendor DLL. Source use needs `src/magstripe`; the existing
`ERDCardMagStripe` runtime package still requires only `rtl`.

## Profiles and operation boundaries

| Explicit profile | Protocol source | Implemented operations | Pending validation |
| --- | --- | --- | --- |
| `msrp206ThreeTrackHL` | MSR206 PM017-U Rev G, target MSR206-3HL | Three-track ISO reads; all-three nonempty programming with explicit high/low coercivity | Delphi/Windows, real firmware/model identity, swipe and physical programming tests |
| `msrp605ThreeTrack` | MSR605 manual cover Rev B, target three-track serial/virtual-COM device | Same operations, with explicit Track 1/3 BPI configuration | Actual device/driver/firmware and USB virtual-COM compatibility |
| MSR206-1/-2/-5 | Other physical track combinations | Not implemented by these profiles | Exact combination semantics and hardware checks |
| MSR206-7HL Rev F | Different command family, including `@` arm/write and `^` acknowledgement | Implemented by a [separate USI1/7O1 adapter](MSR206_7HL.md), including selected-track same-swipe read-back | Physical/Delphi validation; never used as fallback |
| MSR605X/MSR606/MSRE206, Bluetooth, raw/AAMVA/JIS | Different or unverified backends/formats | No inherited support claim | Explicit protocol and hardware profiles |

Choose the actual profile deliberately. A communication test and model reply
`ESC 3 S` confirm the expected three-track response shape; they do not authenticate
brand, prove HL hardware or identify firmware. The manuals' firmware-version
response descriptions are inconsistent, so this implementation does not invent
version parsing or claim a verified firmware release. Profile names identify
protocol documents, not physical certifications.

Reading accepts any nonempty requested track subset. Every supplied track and the
global response status must be valid; decoder errors are not silently converted
to missing data. Ordered absent/empty fields are accepted. No Track 2 mirroring,
resynchronization, raw-format probing or alternate-device fallback occurs.

Programming requires **all three tracks, each nonempty**. The manuals do not
establish whether omitted/empty write fields preserve or erase physically present
tracks; partial/empty programming and erase are therefore refused. This is an
operation-specific limit, not a promise that a device can preserve arbitrary
unselected tracks. Standard payload capacities remain 76/37/104 characters.

An explicit `mscLow` or `mscHigh` is required. `mscCurrent` is refused before
opening the device because preparation resets it and could alter the previous
coercivity setting. After setting the requested mode, `ESC d` must confirm `L`
or `H` before the programming command. This reads the encoder setting; it does
not measure the card's material. No automatic coercivity detection occurs.

## Device status versus host read-back

These protocols return **`ESC 0` status after writing**, not acquired track bytes.
The manuals describe encode/verify capability, but a status reply cannot be
presented as independent host read-back. `TMsr206MagStripeAdapter` therefore has:

- `IMagStripeDevice` for reads, with `VerifiedWrite=false` and no `WriteTracks`
  capabilities. The existing component `WriteTracks` method still requires actual
  same-card read-back and rejects this adapter before acquisition.
- `IMagStripeStatusWriter` for the explicit component `ProgramTracks` method,
  advertising the exact all-three combination and high/low modes.

`ProgramTracks` returns `TMagStripeProgrammingReceipt`: requested tracks/mode,
raw vendor success status and `HostReadBackVerified=false`. Requested metadata is
not measured card data. The adapter never echoes input strings as read-back and
never requests a later swipe as if it verified the programmed card. Other future
status writers can advertise different exact combinations and success statuses;
the generic component does not hardcode MSR206's `30` success byte.

```pascal
uses System.SysUtils, ERD.Card.MagStripe, ERD.Card.MagStripe.Tracks,
  ERD.Card.MagStripe.Serial, ERD.Card.MagStripe.MSR206;

var
  Component: TMagStripeReaderWriter;
  Data: TMagStripeTracks;
  Receipt: TMagStripeProgrammingReceipt;
begin
  Component := TMagStripeReaderWriter.Create(nil);
  try
    Component.Device := TMsr206MagStripeAdapter.Create(
      CreateWindowsMagStripeSerialPort('COM12'), msrp206ThreeTrackHL);
    Component.TimeoutMs := 10000;
    Data[mstTrack1] := '01';
    Data[mstTrack2] := '23';
    Data[mstTrack3] := '45';
    // Explicitly arms programming and waits for a physical swipe.
    Receipt := Component.ProgramTracks([mstTrack1, mstTrack2, mstTrack3], Data, mscHigh);
    // Receipt.DeviceStatus = $30; Receipt.HostReadBackVerified = False.
  finally
    Component.Free;
  end;
end;
```

These are synthetic payloads from the manual's protocol example. This code is a
hardware programming example; the supplied console example is read-only.
A normal read uses `Component.ReadTracks([mstTrack1, mstTrack2, mstTrack3])`.

## Wire, deadline and cleanup

All operation I/O shares one monotonic deadline, including protocol preparation
and waiting for the swipe. Setup cannot consume a full timeout and then restart
it for each response byte. A backward-moving clock is refused. Port acquisition
and final cleanup are separate lifecycle stages; cleanup has a separate bounded
500 ms reset-send budget.

Preparation discards buffered input, sends reset, tests communication, confirms
three-track model, sets BPC 7/5/5 and sets Track 2 to 75 BPI. MSR605 additionally
sets Tracks 1/3 to 210 BPI using its documented density selectors. It changes
reader settings rather than preserving a previous nonstandard reader mode.
Programming then sets/confirms explicit coercivity and sends one complete
`ESC w / ESC s / track fields / ? FS` command. Sentinels, parity and LRC are
provided by the encoder; the command carries unframed payloads.

The maximum write command is 229 bytes. The maximum complete read response is
235 bytes, including three framed track fields, the separate `? FS` block
terminator and `ESC/status`. Input is read one byte at a time within this fixed
bound. A track end sentinel and block question-mark are separate bytes; the
manual's full read example ends the last track with `?? FS`.

No send/receive, denied status, partial write or malformed response is retried.
A failed operation poisons the session until release. Release attempts reset if
commands were sent, then closes exactly once and clears local ownership. Reset
has **no acknowledgement**: successful host transmission is not proof of device
cancellation. An uncertain result requires device reinitialization and physical
inspection rather than an automatic repeat. The next operation always resets and
checks communication/model before arming a new request. No erase/rollback command
is sent during cleanup. Primary reset errors survive secondary close errors.

The component conservatively reports every error after invoking the status
programmer, including preparation errors and release failures, as
`EMagStripeWriteUncertain`. The directly used adapter can distinguish its own
pre-program setup failure from the boundary immediately before programming
transmission. After that boundary all errors are uncertain and exclude underlying
error text/card data. Neither path automatically repeats a programming command.

## Native Windows transport

The native factory accepts only bare ASCII `COM1` through `COM65535`, case
insensitively, and constructs the extended `\\.\COMn` name itself. Arbitrary paths
and file devices are refused. It opens exclusively with `CreateFileW`, configures
9600 baud/8N1 with binary mode and no flow control, and discards RX only. Every
send/one-byte receive sets nonzero total `COMMTIMEOUTS` from the remaining budget.
A short or overreported send is an error, not permission to send the remainder.
Timeout/failed/invalid-size reads return no successful byte.

Handles are pointer-sized; native DCB/COMMTIMEOUTS sizes are checked, with explicit
pointer parameters at the ABI. Configuration failure closes the acquired handle.
Constructors do not open ports; destruction best-effort closes remaining ownership.
Calls are synchronous on one thread without reentrancy or VCL message pumping.
Driver compliance with Windows timeout behavior still needs real Windows checks.
On other platforms native opening is explicitly unsupported; an application may
supply a different `IMagStripeSerialPort` implementation.

Microsoft SDK references: [DCB](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-dcb),
[COMMTIMEOUTS](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-commtimeouts),
[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew),
[WriteFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile).

## Evidence and remaining checks

Protocol facts were checked against vendor-authored manuals mirrored in
[`dev-zzo/libmsr` at commit d0df43e3b7e69439932b9bf67c87d91cbed8a75f](https://github.com/dev-zzo/libmsr/tree/d0df43e3b7e69439932b9bf67c87d91cbed8a75f/docs).
Downloads retained TLS verification; the PDF hashes were verified against the
pinned files. Manuals and third-party implementations are not redistributed.

- MSR206 PM017-U **Rev G**, 2005-04-06: sections 6–9, exact initialization,
  01/23/45 write/read examples, status, BPC, density and coercivity commands.
  SHA-256 `f21599231e8e61c90f054507024a4d2b83a24680b70da00dbcca8d3cdae8db8b`.
- MSR605 cover **Rev B**, 2009-06-01; internal footer says Rev A. The profile uses
  the explicit command descriptions in this pinned edition, including extended
  density selectors; it does not infer a different firmware/SDK revision.
  SHA-256 `c8b9a96479bc6bb1b44093bbb6959dc6e17cc10b3ffe9923c3f26ef94f65b0a7`.
- MSR206-7HL **Rev F**, examined to establish the incompatible command family;
  not implemented by this adapter.
  SHA-256 `087f8fbc7dbaae8284a927c8d655506754cf5b240cb6915fac940bd6ae6f0810`.

`tests/magstripe/Msr206.Tests.dpr` tests independent published frames, all status
values, frame limits, track identities, all seven generic programming combinations,
complete protocol/component chains, every send/receive failure and each programming
reply-byte corruption. It verifies shared deadline expiry, poisoned sessions,
preflight, precise status-only receipts and uncertainty/cleanup behavior.
`NativeSerial.Tests.dpr` exercises actual Windows-call branches against an isolated
Linux C shim, including UTF-16 COM paths, 64-bit handles, DCB/timeouts, partial I/O,
cleanup and a full component/adapter/native-port programming transcript. It does
not test Windows calling conventions or a real driver/device.

`examples/magstripe/InspectMsr206.dpr` provides hardware-free `--help` and
`--frame-hex`, plus explicit Windows port/profile reading. It prints lengths only,
never programs a card and is smoke-tested with a published frame/failed status.
Public APIs have XML documentation. Free Pascal execution and the existing source
readers supplement Delphi; dcc32/dcc64, runtime packages, IDE Help Insight and real
swipe/write/cancellation compatibility remain pending. No physical stripe was
written during validation. See [magstripe foundations](MAGSTRIPE.md) and
[the validation record](VALIDATION.md).
